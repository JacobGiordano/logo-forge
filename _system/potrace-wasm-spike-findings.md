# Spike findings: potrace-wasm (issue #12)

Status: spike complete, throwaway harness kept for reproducibility, nothing wired into the shipped app. `js/` and `css/` are untouched by this session — `git status` confirms zero changes outside `_system/`.

## How this was run

Rather than hacking `buildTraceOptions()` live in `js/app.js` (the instructions' fallback suggestion), I drove the **real running app** end-to-end with Playwright (`_system/potrace-spike/compare.mjs`) — upload → click Trace → read the rendered result back out of the DOM — so every comparison uses the app's actual `preprocessImageData`/`buildTraceOptions`/`cleanupSVG` output, not a reimplementation of it. `esm-potrace-wasm@0.5.1`'s `dist/index.js` was vendored unmodified into `_system/potrace-spike/vendor/potrace-wasm.js` (75,989 bytes, matches #11's research exactly) and loaded via dynamic `import()` from inside the harness page, exactly as #11 proposed for a real integration.

Test images: the existing `tests/fixtures/test-logo.png` (32×32 checkerboard, read-only, not modified) plus three synthetic logos generated in-page (`ring` — a donut with one true topological hole, to stress-test winding; `blob` — a smooth wobbly silhouette, to judge curve quality; `bands` — five concentric flat-color rings, for Track B). Regenerate everything with `node _system/potrace-spike/compare.mjs` (needs `npx serve . -l 4321` running); outputs land in `_system/potrace-spike/out/` (gitignored-by-convention, not committed — regenerate on demand).

One early false start worth naming since it shaped the harness: `app.js` declares `currentSVG`/`currentMaskPreview`/`currentTraceStats` as top-level `let` in a classic script, so they're script-scope, not `window.*` — reading `window.currentSVG` from outside silently returns `undefined`. Fixed by reading the same data back out of the DOM (`renderSVGTab` writes it there), which is arguably more honest anyway since it's what a user actually sees.

## Track A — binary swap

| case | app (imagetracer) | potrace-wasm (same binary mask) |
|---|---|---|
| checkerboard 32×32 | 512 B, 1 path, trace ~220ms | 1289 B, 2 `<path>` (one per color), trace ~3ms |
| ring (donut, 1 hole) | 662 B, 1 path/1 hole, ~230ms | 1356 B, 3 `<path>`, ~4ms |
| blob (smooth silhouette) | 793 B, 1 path, ~245ms | 1896 B, 2 `<path>`, ~2ms |

**Visual quality**: rendered output is essentially indistinguishable between the two pipelines on all three cases — same silhouette, same hole placement, comparably smooth curves on the blob. Potrace's raw byte size is larger, but that's not a fair apples-to-apples number: the app's `compactPathData()` rounds/trims coordinates before comparison and potrace's raw output hasn't had any equivalent precision reduction applied — a real integration would need to add that step (feasible, `roundcoords`-equivalent rounding on potrace's `d` output before merge), not a fundamental cost difference. Potrace's own trace call is fast (single-digit ms) — the app's ~220-245ms per trace is dominated by its own mask pipeline (Otsu threshold, despeckle, hole-fill, smoothing passes) which is unrelated to and untouched by this swap; the curve-fitting stage itself is not the app's bottleneck today.

**Winding/fill-rule finding (the #11 risk)** — two real things were found, one a genuine risk that's now resolved empirically, one a separate integration detail:

1. **Coordinate transform, not winding, was the first trap.** Potrace's `d` coordinates live in its own internal space — 10× scale, Y-flipped — and are only correct when rendered inside the `<g transform="translate(0,H) scale(0.1,-0.1)">` wrapper it emits alongside them. A first pass at the naive "just concatenate potrace's raw `d` strings the way `cleanupSVG` concatenates imagetracer's" produced a **blank render** — not a winding bug, just points 10× too large and off-canvas. A real implementation must carry or bake in that transform before merging paths. This is a new, concrete finding beyond what #11 flagged — worth calling out explicitly since it's an easy trap for whoever implements this for real.
2. **Fill lives on the wrapping `<g>`, not the `<path>`**, for potrace's output — `cleanupSVG`'s `isLightColor(path.getAttribute('fill'))` filter, unmodified, would silently treat every potrace path as "no fill" and discard it. Needs inherited-fill resolution.
3. **Once both of the above are corrected**, taking potrace's per-color `d` output (including its hole subpaths) and dropping it into `cleanupSVG`'s exact existing logic — concatenate + single `<path fill-rule="evenodd">` — **renders pixel-correctly** on the donut/checkerboard/blob cases, matching the app's own current output exactly. Potrace's native convention is unspecified `fill-rule` (SVG default `nonzero`, confirmed — no `fill-rule` attribute appears anywhere in its output) with directional winding for holes, but for the single-hole-depth, non-self-intersecting contours a bitmap tracer produces, `evenodd` and `nonzero` agree — evenodd only cares about crossing parity, and potrace's outer+hole subpaths are simple non-overlapping nested loops, so the parity computation lands on the same answer regardless of which winding direction potrace happened to pick. **This was not assumed — it was verified by rendering and visually diffing against the app's real output**, per #11's ask.
4. **Caveat**: only tested up to one level of nesting (single hole). A hole containing a same-color island (hole-in-hole, two levels deep) was not tested and is the one topology where evenodd/nonzero could in principle diverge depending on potrace's exact winding convention at each nesting level — worth a targeted test before shipping if the app's `hole-preservation` feature is expected to produce that topology in practice (plausible for letterforms like "B" or "8").

## Track B — color-aware comparison

This is the more interesting result. The app's current forced-binary pipeline, run on a 5-band concentric-ring test logo, collapses all tonal structure into a single flat black circle — exactly the limitation #11's framing predicted. Feeding the **same original (non-binarized) image** directly to potrace-wasm's own `extractcolors`/`posterizelevel` machinery (it does its own posterization internally — no manual per-layer bitmap splitting was needed, contrary to what the spike brief anticipated might be required) reconstructs all five color bands with good color fidelity, visually much closer to the source and to what an Illustrator Live Trace of the same image would produce.

However: inspecting the actual SVG behind that clean-looking render surfaced a real problem. At `posterizelevel=6` the output was **81 `<path>` elements for a 5-ring image — 75 of them (93%) under 100 characters, i.e. tiny speckle fragments** from anti-aliased color-boundary noise, with only 6 paths doing the real work. This didn't show up visually at render size but bloats the SVG (9.7KB for what should be a ~1-2KB, 5-path image) and would get worse, not better, on a real uploaded logo (JPEG compression artifacts, gradients, noisy scans) — exactly the kind of input this app exists to clean up. The app's current binary pipeline avoids this entirely because `preprocessImageData`'s despeckle/hole-fill/smoothing passes run *before* tracing; potrace's own `turdsize` param (despeckle-equivalent) was set to 2 for this test and didn't prevent the fragmentation — it would need real tuning, and possibly a per-layer cleanup pass modeled on the app's existing mask pipeline, generalized from 1 bit to N color layers.

## Recommendation

**Binary swap (Track A): worth pursuing as a real implementation issue.** The winding risk #11 flagged is resolved — verified empirically, not assumed — conditional on carrying potrace's coordinate transform and resolving inherited fill, both straightforward, well-understood fixes now that they're identified. Effort roughly matches #11's **M** estimate; if anything slightly lower now that two of the "needs empirical verification" unknowns are closed. Remaining real work: the transform-baking step (new, not in #11's plan), precision/rounding parity for fair file-size comparison, the untested hole-in-hole topology, and the slider remapping (`ltres`/`qtres`/`rightangleenhance` → `alphamax`/`opttolerance`) #11 already scoped.

**Color-aware (Track B): promising but not ready — needs a follow-on spike of its own before it's an implementation issue, not a straight bolt-on to the Track A work.** The quality ceiling is real and visually compelling, but the speckle-fragmentation problem means it can't just be "turn on `extractcolors`" — it needs either aggressive `turdsize` tuning validated against several real (not synthetic) logo photos/scans, or a proper pre-trace cleanup pass per color layer analogous to what `preprocessImageData` already does for the binary path, generalized to N layers. That's a meaningfully bigger effort than Track A alone — call it **M–L**, and it should stay decoupled: Track A can ship on its own merits (it's a drop-in quality/speed improvement to the existing binary pipeline with no new UI), while Track B would be a genuinely new feature (multi-color tracing, new UI controls, new export considerations for multi-color SVGs) layered on top later, once the speckle problem has a validated fix.

**Not recommended as a single combined issue.** Track A is low-risk and additive (falls back cleanly, per #11 §4, to today's exact behavior on any environment where wasm is unavailable). Track B is higher-risk and needs more validation before committing UI/scope to it. Splitting them avoids blocking the safe, well-understood win on the unresolved one.
